# CRM-система — веб-приложение для управления клиентами

Учебный проект: CRM-система на Django для работы с услугами, рекламными кампаниями,
потенциальными и активными клиентами, контрактами и статистикой рекламных кампаний.

## 🛠 Стек технологий

| Технология | Назначение |
|---|---|
| Python 3.9+ | язык программирования |
| Django | веб-фреймворк |
| PostgreSQL | СУБД |
| psycopg2-binary | драйвер подключения Django к PostgreSQL |
| Pylint | проверка кода на соответствие PEP 8 |

## 📋 Функциональность (по ТЗ)

- Авторизация пользователя
- Создание, редактирование и просмотр предоставляемых услуг
- Создание, редактирование и просмотр рекламных кампаний
- Создание, редактирование и просмотр потенциальных клиентов
- Создание, редактирование и просмотр контрактов
- Перевод потенциального клиента в активного
- Подсчёт и отображение статистики по рекламным кампаниям:
  сколько привлечено потенциальных клиентов, сколько из них перешло в активных,
  соотношение дохода от контрактов и расходов на рекламу
- Ролевая модель: Администратор, Оператор, Маркетолог, Менеджер

## 🚀 Установка и запуск (Linux / Ubuntu)

### Шаг 1. Требования

- Python 3.9 или новее
- PostgreSQL 14 или новее

### Шаг 2. Получить код проекта

Склонируйте репозиторий (или распакуйте архив) и перейдите в папку проекта:

```bash
git clone <адрес репозитория>
cd crm_project
```

### Шаг 3. Виртуальное окружение

```bash
python3 -m venv venv
source venv/bin/activate
```

После активации в начале строки терминала появится `(venv)`.

### Шаг 4. Установка зависимостей

```bash
pip install -r requirements.txt
```

### Шаг 5. Создание базы данных

Подключитесь к PostgreSQL:

```bash
sudo -u postgres psql
```

Создайте базу данных и выйдите:

```sql
CREATE DATABASE crm_db;
\q
```

Параметры подключения задаются в `config/settings.py` в блоке `DATABASES`
(NAME, USER, PASSWORD, HOST, PORT) — при необходимости укажите свои значения.

### Шаг 6. Миграции: инициализация и накат

Миграции (файлы в папках `*/migrations/`) входят в состав проекта.
Для инициализации базы достаточно **накатить** их:

```bash
python manage.py migrate
```

Если вы вносили изменения в модели, сначала создайте новые миграции:

```bash
python manage.py makemigrations
python manage.py migrate
```

Проверить список созданных таблиц:

```bash
psql -d crm_db -c '\dt'
```

### Шаг 7. Создание суперпользователя

```bash
python manage.py createsuperuser
```

Команда запросит логин, email и пароль. Суперпользователь получает доступ
к административной панели Django, через которую создаются пользователи
и назначаются роли (требование ТЗ).

### Шаг 8. Загрузка тестовых данных (фикстуры)

```bash
python manage.py loaddata fixtures/data.json
```

Подробнее — в разделе «📦 Фикстуры».

### Шаг 9. Запуск сервера разработки

```bash
python manage.py runserver
```

- Приложение: http://127.0.0.1:8000/
- Административная панель: http://127.0.0.1:8000/admin/

## 📦 Фикстуры

Фикстура — это JSON-файл со снимком данных из базы. Проект содержит
`fixtures/data.json` с тестовыми данными: услуги, рекламные кампании,
потенциальные клиенты, контракты, активные клиенты.

### Загрузка фикстур в базу

```bash
python manage.py loaddata fixtures/data.json
```

Команда сама учитывает зависимости между таблицами (кампания ссылается на
услугу, лид — на кампанию и т.д.), отдельный порядок загрузки указывать не нужно.

**Важно:** фикстуры хранят только пути к файлам контрактов (FileField),
сами файлы лежат в папке `media/` и поставляются вместе с проектом.

### Как создать / обновить фикстуру из текущей базы

```bash
python manage.py dumpdata services.Service campaigns.Campaign \
    leads.Lead contracts.Contract clients.ActiveClient \
    --indent 2 -o fixtures/data.json
```

## 🔐 Аутентификация и авторизация

### Аутентификация пользователей

Используется стандартный механизм аутентификации Django (`django.contrib.auth`):

- учётные записи хранятся в таблице `auth_user` в PostgreSQL;
- пароли хранятся только в виде хэшей, в открытом виде Django их не хранит;
- сессии пользователей — таблица `django_session`;
- создание пользователей и назначение ролей выполняется администратором
  через административную панель Django (требование ТЗ);
- страницы входа и выхода реализованы на базе стандартных представлений
  Django (`LoginView`, `LogoutView`).

### Авторизация по ролям

Роли реализуются через стандартные **группы** Django (`django.contrib.auth.models.Group`).
Каждой роли соответствует группа, которой в админке назначаются права
(permissions) на модели: `add_`, `change_`, `view_`, `delete_` для
соответствующих сущностей.

Логика проверки доступа:

1. Все представления CRM наследуются от `LoginRequiredMixin` —
   неавторизованный пользователь перенаправляется на страницу входа.
2. Для проверки роли используется проверка принадлежности пользователя
   к группе (или `PermissionRequiredMixin` с проверкой конкретных permissions) —
   пользователь без нужной роли получает ошибку 403.
3. В шаблонах элементы интерфейса (кнопки, пункты меню) дополнительно
   скрываются по роли. Это UX-уровень; основной контроль доступа — серверный.
